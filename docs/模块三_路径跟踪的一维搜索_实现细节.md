# 模块三：路径跟踪的一维搜索 — 实现细节

> 本文档基于 `include/bezier_tracking/path_planner.hpp` 和 `src/path_planner.cpp` 的源代码，对算法核心模块三的实现进行逐层拆解。模块三负责：**在每个控制周期，通过一维搜索找到虚拟机器人（pursuee）在分段贝塞尔路径上的最优初始参数 $\lambda$，使得真实机器人（pursuer）的追踪轨迹代价最小**。

---

## 一、模块概述

模块三是连接"路径参数化"（模块二）和"追踪动力学"（模块一）的桥梁。它将原本复杂的轨迹优化问题降维为对单一参数 $\lambda$ 的搜索，是算法**实时性**的关键保障。

### 核心任务

| 阶段 | 函数 | 职责 |
|---|---|---|
| 初始化 | `priming()` | 在仿真开始前，全局搜索所有曲线段，找到最优的初始 $\lambda$ |
| 运行期 | `tracking()` | 每个控制周期，从当前 $\lambda$ 出发，局部搜索找到使轨迹代价最小的 $\lambda^*$ |

### 输入输出

| 输入项 | 说明 |
|---|---|
| `x0, y0` | 机器人当前位置 |
| `theta0` | 机器人当前航向 |
| `lambda`（内部状态） | 当前估计的虚拟机器人在全局路径上的参数位置 |

| 输出项 | 说明 |
|---|---|
| `trajectory` | 对应最优 $\lambda^*$ 的模拟轨迹（位置、速度、总代价） |

`tracking()` 并不直接输出速度命令给机器人，而是返回**对应最优参数 $\lambda^*$ 的完整模拟轨迹**。外层调用者（如 `demo_*.cpp` 中的控制循环）会从这个轨迹中提取**第一个速度命令**应用于真实机器人，这正是"类 MPC 的滚动时域实现"——只应用第一个控制量，下一周期重新规划。

### 外部调用者如何使用 `tracking()` 的输出

以 `example/demo_linear_bezier.cpp` 中的控制循环为例：

```cpp
planner.priming(x_current, y_current, theta_current);
for (int i = 0; i < tsteps; i++) {
    // 1. 调用 tracking() 获取最优轨迹
    trajectory = planner.tracking(x_current, y_current, theta_current);

    // 2. 提取轨迹中的第一个速度命令（vel[0]）
    vx = trajectory.vel[0][0];
    vy = trajectory.vel[0][1];

    // 3. 用该速度更新机器人状态（前向欧拉积分）
    x_next = x_current + vx * planner.get_dt();
    y_next = y_current + vy * planner.get_dt();
    theta_next = planner.find_angle(1, 0, vx, vy);

    // 4. 更新当前状态，进入下一控制周期
    x_current = x_next;
    y_current = y_next;
    theta_current = theta_next;
}
```

**关键细节**：
- `trajectory.vel[0]` 是追踪动力学（模块一）在第一步产生的速度向量，已满足 ICR 约束；
- 机器人状态更新使用简单的前向欧拉积分：`x_next = x + vx * dt`；
- 航向通过 `find_angle()` 从速度向量反推，而非直接积分角速度；
- 循环的下一周期会重新调用 `tracking()`，此时 `PathPlanner` 内部的 `lambda` 状态已在上一次调用中被更新，搜索从新的最优解附近开始。

## 二、priming() — 初始化阶段的全局搜索

### 2.1 源码

```cpp
void PathPlanner::priming(float x0, float y0, float theta0){
    Trajectory trajectory;
    float cost_min;
    float lambda_best;
    int num_curves = params_.map->get_num_curves();

    lambda = 0;
    trajectory = tracking(x0, y0, theta0);
    cost_min = trajectory.total_cost;
    lambda_best = lambda;

    for (float lambda_test = 1; lambda_test < num_curves; lambda_test += 1){
        lambda = lambda_test;
        trajectory = tracking(x0, y0, theta0);
        if (trajectory.total_cost < cost_min){
            lambda_best = lambda;
        }
    }

    lambda = lambda_best;
    std::cout << "lambda_best = " << lambda << std::endl;
}
```

### 2.2 算法逻辑

`priming()` 在仿真开始前执行一次，目的是**避免冷启动时的盲目搜索**。它采用粗粒度的网格搜索策略：

1. **测试第 0 段起点**（`lambda = 0`）：调用 `tracking()` 获得轨迹代价，设为当前最优；
2. **遍历所有段起点**（`lambda = 1, 2, ..., num_curves-1`）：对每段起点调用 `tracking()`，如果代价更低则更新最优；
3. **设置全局最优 $\lambda$**：将 `lambda` 状态变量设为最优值，供后续 `tracking()` 使用。

### 2.3 搜索策略分析

| 特性 | 说明 |
|---|---|
| 搜索空间 | 所有贝塞尔曲线段的起点（`lambda = 0, 1, 2, ...`） |
| 搜索粒度 | 每段只测试起点（`lambda_test += 1`），不测试段内位置 |
| 调用代价 | 每测试一个点调用一次 `tracking()`，每次 `tracking()` 内部又多次调用 `pursuitcurve_sim()` |

**为什么只搜索段起点？**

- 段起点是路径的"逻辑节点"，通常对应方向变化或路径过渡点；
- 从段起点开始跟踪，虚拟机器人的初始航向与段的起始切向一致，减少不必要的航向代价；
- 粗粒度搜索在初始化阶段是可接受的，因为 `priming()` 只执行一次。

**潜在问题**：
- 如果最优的虚拟机器人初始位置位于某段内部（而非起点），`priming()` 可能错过它；
- 但对于后续 `tracking()` 的局部搜索而言，`priming()` 只需要提供一个"足够好"的初始值即可。

## 三、tracking() — 运行期的局部一维搜索

### 3.1 源码

```cpp
PathPlanner::Trajectory PathPlanner::tracking(float x0, float y0, float theta0){
    Trajectory traj_forward, traj_backward;
    Trajectory traj_best, traj_test;
    float lambda_diff = params_.map->get_lambda_diff(lambda);
    
    traj_best     = pursuitcurve_sim(x0, y0, theta0, lambda);
    traj_forward  = pursuitcurve_sim(x0, y0, theta0, lambda + lambda_diff);
    traj_backward = pursuitcurve_sim(x0, y0, theta0, lambda - lambda_diff);

    if (traj_forward.total_cost <= traj_backward.total_cost){
        // 前向更优，沿前向搜索
        while(true){
            if (traj_best.total_cost <= traj_forward.total_cost){
                return traj_best;
            }
            else{
                traj_best    = traj_forward;
                lambda      += lambda_diff;
                lambda_diff  = params_.map->get_lambda_diff(lambda);
                traj_forward = pursuitcurve_sim(x0, y0, theta0, lambda + lambda_diff);
            }
        }
    }
    else{
        // 后向更优，沿后向搜索
        while(true){
            lambda_diff = params_.map->get_lambda_diff(lambda);
            if (traj_best.total_cost <= traj_backward.total_cost){
                return traj_best;
            }
            else{
                traj_best     = traj_backward;
                lambda       -= lambda_diff;
                lambda_diff   = params_.map->get_lambda_diff(lambda);
                traj_backward = pursuitcurve_sim(x0, y0, theta0, lambda - lambda_diff);
            }
        }
    }
}
```

### 3.2 算法逻辑拆解

`tracking()` 的搜索过程可以分为三个清晰的阶段：

#### 阶段 1：初始评估（3 次仿真）

```
当前点:    λ
前向点:    λ + λ_diff
后向点:    λ - λ_diff
```

对三个点分别调用 `pursuitcurve_sim()`，获得三条轨迹及其总代价。

#### 阶段 2：选择搜索方向

```
if (cost(λ + λ_diff) <= cost(λ - λ_diff)):
    选择前向搜索
else:
    选择后向搜索
```

**注意**：这里的比较不是与当前点 `λ` 比较，而是**前向点和后向点互相比较**。这意味着：
- 即使当前点 `λ` 本身就是局部最优（`cost(λ) < cost(λ ± λ_diff)`），算法也会先选择"看起来更有希望"的方向进行一次额外验证；
- 这种设计避免了在两个方向上都做无用搜索，是一种**贪心策略**。

#### 阶段 3：沿选定方向贪心前进

以**前向搜索**为例：

```
while true:
    if cost(当前) <= cost(前向一步):
        return 当前轨迹   ← 找到局部最优，停止
    else:
        当前 = 前向       ← 向前移动一步
        λ += λ_diff
        重新计算前向一步的轨迹
```

**这是一个典型的贪心线性搜索（Greedy Line Search）**，而非报告原文中提到的"数值梯度下降"。

### 3.3 算法本质：贪心线性搜索

准确地说，`tracking()` 实现的是一种**离散空间中的贪心爬山算法**：

| 特性 | 说明 |
|---|---|
| 搜索空间 | 一维离散网格，网格间距为 `lambda_diff` |
| 搜索策略 | 贪心：每步只比较相邻两点，沿代价下降方向移动 |
| 终止条件 | 当前点代价 ≤ 前向/后向点代价 |
| 收敛保证 | 保证找到**离散空间中的局部最优**（因为每步严格下降，且空间有限） |
| 全局最优 | **不保证**找到全局最优，取决于初始点和 landscape 形状 |

**与梯度下降的区别**：

| 梯度下降 | tracking() 的贪心搜索 |
|---|---|
| 使用梯度方向（一阶导数）确定搜索方向 | 使用相邻两点的代价比较确定方向 |
| 步长可自适应（如回溯线搜索） | 步长固定为 `lambda_diff` |
| 连续参数空间 | 离散参数空间 |
| 可能 overshoot | 不会 overshoot，因为每步只走一个网格 |

### 3.4 lambda_diff 的动态更新

代码中有一个容易忽略的细节：

```cpp
lambda_diff = params_.map->get_lambda_diff(lambda);
```

这行代码在循环体内被**多次调用**。由于 `Map::get_lambda_diff()` 返回当前段对应的搜索步长，当搜索跨越段边界时，`lambda_diff` 会自动更新为新段的步长。

**示例**：
- 假设第 0 段弧长 2m，`dstep = 0.1`，则 `lambda_diff_0 = 0.1/2 = 0.05`
- 假设第 1 段弧长 4m，`dstep = 0.1`，则 `lambda_diff_1 = 0.1/4 = 0.025`
- 当搜索从 `lambda = 0.95`（第 0 段）移动到 `lambda = 1.02`（第 1 段）时，步长自动从 0.05 变为 0.025

这确保了搜索步长在**几何空间**中大致均匀，而不是在参数空间中均匀。

## 四、代价函数 Landscape 的分析

### 4.1 代价函数的构成

代价在 `pursuitcurve_sim()` 中累积计算：

$$J(\lambda) = \sum_{i=0}^{horizon} \left[ w_1 \cdot d_i + w_2 \cdot |\alpha_i| + w_3 \cdot |\Delta\theta_i| \right]$$

其中：
- $d_i$：第 $i$ 步 pursuer 与 pursuee 的距离
- $\alpha_i$：第 $i$ 步两机器人速度向量的夹角
- $\Delta\theta_i$：第 $i$ 步 pursuer 的航向变化量（受 ICR 约束后）

### 4.2 Landscape 的形状特征

代价函数 $J(\lambda)$ 的 landscape 具有以下特征：

**1. 多峰性（Multimodality）**

由于追踪曲线动力学的非线性，不同的初始 $\lambda$ 可能导致截然不同的追逐轨迹。如 README 中展示的：
- `farleft`：初始 $\lambda$ 过左，导致 180 度掉头，代价极高；
- `farright`：初始 $\lambda$ 过右，收敛缓慢，代价中等；
- `middle`：初始 $\lambda$ 适中，快速平滑收敛，代价最低。

这意味着 $J(\lambda)$ 可能存在多个局部极小值，贪心搜索可能陷入次优解。

**2. 非对称性**

前向搜索和后向搜索的 landscape 可能不对称：
- 如果机器人当前位于路径前方，增大 $\lambda$（向前）通常更优；
- 如果机器人当前位于路径后方，减小 $\lambda$（向后）可能更优。

`tracking()` 通过比较 `traj_forward` 和 `traj_backward` 的代价来处理这种非对称性。

**3. 段边界处的间断性**

当 $\lambda$ 跨越整数边界（段边界）时：
- 贝塞尔曲线的切向可能突变（如果相邻段未保证 $C^1$ 连续）；
- `lambda_diff` 的值会改变；
- 这些都可能导致 $J(\lambda)$ 在段边界处出现跳跃或不连续。

### 4.3 搜索失败的场景

| 场景 | 原因 | 后果 |
|---|---|---|
| 两个局部极小值之间 | 贪心搜索从一侧出发，无法跨越中间的山峰到达另一侧 | 收敛到次优解，跟踪性能下降 |
| 代价 landscape 平坦 | 多个相邻点的代价相近 | 搜索在第一个满足条件的点停止，可能未找到真正最优 |
| 段边界切向突变 | $J(\lambda)$ 在边界处不连续 | 搜索可能跳过最优解，或在边界处震荡 |

## 五、关键设计决策与潜在问题

### 5.1 设计决策分析

**决策 1：贪心策略而非双向搜索**

`tracking()` 在评估前向和后向之后，只选择**一个方向**进行深入搜索。这比双向搜索更高效（最多搜索半个空间），但可能错过另一侧的更好解。

**合理性**：在实时控制中，计算资源有限，贪心策略是合理的折中。此外，由于控制周期很短（`dt = 0.01s`），即使当前周期找到的是次优解，下一周期会从新的位置重新搜索，有机会纠正。

**决策 2：固定步长的离散搜索**

使用 `lambda_diff` 作为固定步长，而非自适应步长（如二分搜索、黄金分割搜索）。

**合理性**：
- 实现简单，无额外逻辑开销；
- `lambda_diff` 已经根据段弧长调整，在几何空间中近似均匀；
- 对于本项目的场景复杂度，固定步长通常足够。

**潜在改进**：
- 可在粗搜索后增加细搜索（如二分搜索），在局部最优附近进一步精确化；
- 可使用抛物线插值近似代价 landscape，减少仿真调用次数。

**决策 3：在运行期保持 lambda 状态**

`lambda` 是 `PathPlanner` 的成员变量，在 `tracking()` 中被更新，在下一控制周期作为初始值使用。

**好处**：
- 利用时间连续性：虚拟机器人的位置不会突变，搜索从上一时刻的最优解附近开始；
- 大幅减少搜索范围（通常只需微调）。

**风险**：
- 如果机器人遭遇突发扰动（如障碍物、定位跳变），上一时刻的 `lambda` 可能完全失效；
- 此时需要类似 `priming()` 的全局重新初始化机制，但代码中未提供。

### 5.2 潜在问题

| 问题 | 触发条件 | 影响 | 现有缓解 |
|---|---|---|---|
| 局部最优陷阱 | 代价 landscape 多峰 | 跟踪轨迹次优，收敛慢或震荡 | 无（依赖滚动时域的渐进修正） |
| 搜索方向错误 | 前向/后向初始评估误导 | 向错误方向搜索，错过更优解 | 无 |
| 越界访问 | `lambda - lambda_diff < 0` 或超出最后一段 | `Map` 类会自动钳制到有效段 | `Map` 的 `clamp` 处理 |
| 计算延迟 | 搜索步数过多 | 无法满足实时控制周期 | `horizon` 和 `dstep` 参数限制 |
| 段边界震荡 | 最优解恰好在边界附近 | 不同周期在不同段间跳动 | 无 |

## 六、性能分析

### 6.1 单次 tracking() 的调用开销

以 `demo_linear_bezier.cpp` 的参数为例：
- `horizon = 150`
- `dt = 0.01s`
- `dstep = 0.1`（默认值）

**最少调用次数**（当前点即最优）：

- `traj_best`：1 次 `pursuitcurve_sim`
- `traj_forward`：1 次
- `traj_backward`：1 次
- 进入循环后，第一次比较即满足终止条件：0 次额外调用
- **总计**：3 次 `pursuitcurve_sim`

**典型调用次数**（需要微调 2-3 步）：

- 初始评估：3 次
- 前进 2-3 步：2-3 次
- **总计**：5-6 次 `pursuitcurve_sim`

**最多调用次数**（极端情况）：

- 假设路径有 3 段，搜索跨越整段：约 `1/dstep = 10` 步
- 总计约 13 次 `pursuitcurve_sim`

### 6.2 单次 pursuitcurve_sim() 的内部开销

每次 `pursuitcurve_sim` 执行一个 `horizon+1` 次的循环，每次循环涉及：

- 1 次 `get_point()`（虚函数调用）
- 1 次 `lambda_velocity()`（虚函数调用）
- 1 次 `get_velocity()`（虚函数调用）
- 多次浮点运算（距离、角度、代价）

以 `horizon = 150` 为例，每次 `pursuitcurve_sim` 约 150 次虚函数调用 + 数百次浮点运算。

### 6.3 每控制周期的总开销估算

| 场景 | tracking() 调用次数 | pursuitcurve_sim() 总次数 | 虚函数调用总数 |
|---|---|---|---|
| 最优情况 | 1 | 3 | ~450 |
| 典型情况 | 1 | 5-6 | ~750 |
| 最坏情况 | 1 | ~13 | ~2000 |

对于 `dt = 0.01s`（100Hz 控制频率），在现代 CPU 上通常可以满足实时性，但在资源受限的嵌入式平台上可能需要优化。

## 七、与模块一的交互

### 7.1 调用关系

```
translate to english
请翻译以下内容为英文，保持格式和结构不变：tracking() / priming()
│
├─► pursuitcurve_sim(x0, y0, theta0, lambda)           ← 模块一
│   │
│   ├─► params_.map->get_point(lambda, x_lead, y_lead)      ← 模块二
│   ├─► params_.map->lambda_velocity(lambda, params_.vel)   ← 模块二
│   ├─► params_.map->get_velocity(lambda, lambda_vel, ...)  ← 模块二
│   │
│   └─► 追踪动力学 + ICR 约束 + 代价累积                    ← 模块一
│
└─► 比较代价，更新 lambda，返回最优轨迹
```

### 7.2 交互接口

模块三与模块二通过 `Map` 类的三个函数交互：

```cpp
// 在 pursuitcurve_sim 中
params_.map->get_point(lambda, x_lead, y_lead);              // 获取虚拟机器人位置
lambda_vel = params_.map->lambda_velocity(lambda, params_.vel);  // 获取参数变化率
params_.map->get_velocity(lambda, lambda_vel, vx_lead, vy_lead); // 获取虚拟机器人速度
```

模块三与模块一通过 `pursuitcurve_sim` 的调用交互：

```cpp
// 在 tracking / priming 中
trajectory = pursuitcurve_sim(x0, y0, theta0, lambda);
// 返回：trajectory.pos, trajectory.vel, trajectory.total_cost
```

| "数值梯度下降基于方法" | 贪心线性搜索（比较相邻点代价，沿下降方向移动） | 不是严格的梯度下降，无梯度计算 |
| "一维搜索问题" | 沿全局参数 $\lambda$ 的离散网格搜索 | 搜索空间是一维的，符合描述 |
| "cost function needs to consider distance, heading, smoothness" | `total_cost += distance_cost*distance + heading_cost*abs(angle) + smooth_cost*angle_diff` | 完全对应 |
| "behave like a MPC controller" | 每个周期重新调用 `tracking()`，只应用第一个速度命令 | 类 MPC 的滚动时域实现，符合描述 |

## 九、代码中的隐藏细节

### 9.1 前向与后向搜索的不对称实现

仔细观察代码，前向和后向搜索的实现略有不同：

```cpp
// 前向搜索
while(true){
    if (traj_best.total_cost <= traj_forward.total_cost){
        return traj_best;  // 直接返回
    }
    else{
        traj_best = traj_forward;
        lambda += lambda_diff;
        lambda_diff = params_.map->get_lambda_diff(lambda);  // 更新步长
        traj_forward = pursuitcurve_sim(...);
    }
}

// 后向搜索
while(true){
    lambda_diff = params_.map->get_lambda_diff(lambda);  // 先更新步长
    if (traj_best.total_cost <= traj_backward.total_cost){
        return traj_best;
    }
    else{
        traj_best = traj_backward;
        lambda -= lambda_diff;
        lambda_diff = params_.map->get_lambda_diff(lambda);
        traj_backward = pursuitcurve_sim(...);
    }
}
```

**前向搜索**：在循环**开头**不更新 `lambda_diff`，因为前一次迭代末尾已经更新了；
**后向搜索**：在循环**开头**先更新 `lambda_diff`，因为进入后向分支时 `lambda_diff` 可能还是前向的值。

这是一个**防御性编程**的细节，确保跨越段边界时步长正确。

### 9.2 代价比较的等号处理

```cpp
if (traj_forward.total_cost <= traj_backward.total_cost)
```

使用 `<=` 而非 `<`，意味着当前向和后向代价**完全相等**时，优先选择前向。这在 landscape 对称时是一种确定性的偏置，避免随机选择。

同样：
```cpp
if (traj_best.total_cost <= traj_forward.total_cost)
```

使用 `<=` 意味着：如果前向点的代价**等于**当前点，搜索停止。这是一种保守策略——不冒险移动到代价相同的点。

## 十、小结

模块三是算法**实时性**与**计算效率**的核心保障：

1. **降维策略的成功**：将无穷维轨迹优化降维为单参数搜索，使得在 0.01s 的控制周期内完成规划成为可能；
2. **贪心搜索的务实选择**：虽然理论上不保证全局最优，但在实际场景中配合滚动时域实现，通常能找到足够好的解；
3. **状态连续性利用**：通过维护 `lambda` 成员变量，利用时间连续性大幅缩小搜索范围。

**最值得关注的技术细节**：

- `tracking()` 不是梯度下降，而是**贪心线性搜索**，这一差异影响对算法收敛性的理论分析；
- `lambda_diff` 在循环中动态更新，确保搜索步长在几何空间中均匀，但增加了理解复杂度；
- 前向/后向搜索的不对称实现（`lambda_diff` 更新位置不同）是防御性编程的体现，但也暗示了代码在边界情况下的脆弱性。

**最大的理论缺口**：

- 缺乏对代价 landscape 形状的分析，无法确定贪心搜索在何种条件下失效；
- 缺乏对搜索收敛速度和最优性间隙的定量分析；
- 没有处理"上一时刻的 lambda 完全失效"的应急机制。
